## 3. חקירה פורנזית ממוקדת — ארבעה מוקדי חסימה

### א. מודלים ואובדן מידע

עקוב בפועל אחר מסמך fixture מ-`rawText` עד הייצוא:

`rawText → Lexer/Parser → DocumentModel → MeasuredItems → LineModel → PagePlan → PageModel → Worker transport → DOM/HTML/PDF`.

הצג לכל שלב את ה-input/output, טיפוס הנתונים, זהות, sourceRange, font/run, גאומטריה ו-diagnostics.

בפרט:
- `DocumentModel` כבר מכיל blocks מסוג paragraph. בדוק האם `paragraphs=0` במפה מתייחס לתוצאה אחרת, למודל הישן, למבנה `pages[].cols[].lines`, או לאובייקט שנשלח ל-`signature-compare`.
- `core/page-model.js` כבר כולל `placeLine` עם x/y/w/h, sizePt, baselineY ושדות sizePt/fontKey ברמת המילים כאשר זמינים. אמת האם הנתונים קיימים בכל סוגי השורות, ולא רק בחלקן.
- בדוק את `LineModel` ואת פרגמנטי השורה: שורה אחת עשויה להכיל מספר גופנים, גדלים וסגנונות. אין להוסיף fontKey יחיד ברמת שורה אם הוא מאבד מידע פר-run/fragment.
- בדוק את `PagePlan` ואת `PageModel`: y אבסולוטי שייך לאחר החלטת ה-Planner; אין להוסיף y סמנטי ל-DocumentModel או ל-LineModel.
- בדוק את ה-Worker transport: האם השדות נשמרים ב-JSON, עוברים clone, מאומתים ומוקפאים מחדש.
- אם מידע קיים ב-PageModel אך חסר בחתימת `signature-compare`, תקן קודם את כלי המדידה/ההשוואה או את המיפוי. אל תשנה את המנוע כדי להתאים לכלי שגוי.

הפק פלט JSON מאומת שמונה שדות ברמת האובייקט וברמת fragment/word; הצג ספירה של total/has/missing ונתיב JSON מלא. אין להציג „0/4002” בלי להוכיח ש-4,002 האובייקטים נספרו מתוך PageModel הנכון.

### בדיקת s9d בפרט

הבדיקה מחוברת כעת ל-`npm test`, אך assertion ה-digest אינו משווה לערך נעול. הוסף hash צפוי מאושר רק אם מקור הנעילה ברור ומתועד. אם אין מקור מהימן ל-hash, שנה את טענת הבדיקה לשם מדויק והוסף בדיקת שקילות אמיתית במקום להמציא golden. הרחב binding-offset לשני הטורים ולמקרי parity/recto/verso; בדוק שה-assertion של headerHeight בודק את הסמנטיקה הנכונה.

## 7. שערי בדיקה והוכחה

בסיום העבודה:
1. `npm test` מלא — לתעד פקודה, Node version, exit code וספירות לכל suite.
2. `npm run test:determinism` — השוואה מלאה.
3. `cross-check` — להציג לכל קורפוס בנפרד legacy ו-unified; לא להסיק על unified מבדיקת legacy.

## 10. ממצאי ביקורת משלימים — חובה ליישם לפני כתיבת המפה המתוקנת

קרא גם את `audits/STAGE1_MAP_FORENSIC_FINDINGS_2026-11-19.md`. נספח זה מוסיף עובדות קונקרטיות שיש לטפל בהן:

1. **run-ours אינו PageModel:** `tools/layout-parity/run-ours.js` בונה `ours-model.json` חדש מתוך `result.pages`; הוא אינו מעתיק את `result.pageModel`. שדה `model.meta.engine` אף מקובע למחרוזת legacy, גם בהרצת `--unified`. `paragraphs` מסונתזים לפי `paraId` ב-adapter. לכן יש לסווג מחדש את טענות `paragraphs=0`, `fontKey=0/4002` והיעדר y/sizePt: הן עשויות לשקף adapter שאינו תואם לפרופיל המאוחד, ולא חוסר במודל עצמו. בדוק את PageModel ישירות, ובנפרד את שימור paragraph/block identity עד אליו.
2. **בדיקת s9d של digest:** בדיקת "legacy hash" משתמשת ב-`getDefaultSettings()`, שבאותו קובץ נבדק במפורש כ-`isImudProfile=false`. היא לא מאמתת `legacyProfile`, לא משווה ל-hash צפוי, ורק בודקת מחרוזת ועמודים. אסור לייחס לה legacy non-regression. תקן את מסלול הריצה וההשוואה או שנה את הטענה/שם הבדיקה; אל תמציא hash.
3. **Stage 8:** שש הפרוסות מתועדות כמבוצעות, כולל DOM/HTML/PDF/parity/performance. עדכן את PP-04/05/06 ואת מדדי הביצועים לפי `STAGE8_SLICE6_INVENTORY.md`, אך אל תסיק ש-legacy הוסר.
4. **Stage 9:** 13/13 בשערי shadow v5 הם שערי כיסוי/זהות תוכן, הערות, TOC, H7, PageModel ודקדוק. הם אינם בדיקת parity גאומטרית מלאה (הדוח מציג 695 עמודי legacy מול 896 מאוחד). בנוסף `STAGE9_CUTOVER_MAP.md` אינו מעודכן מול רישום תיקוני 9b.2–9b.5 ב-`ISSUE_REGISTRY.md`. יש לעדכן את המפה, לאתר ריצה עדכנית לאחר 9b.5, ולשמור בנפרד שערי content/geometry/DOM/HTML/PDF/cutover.
5. **תמונות:** לפצל את AS-04 ליכולות שונות: תחביר image inline/DocumentModel; AssetResolver וטעינה/מדידה/Worker/LineModel/PageModel/renderers; משטח UI לצירוף נכסי מסמך (Stage 3 אומר שאינו קיים); ייבוא תמונות DOCX; ונכסי עיצוב/שערים. `docx-import.js` מטפל ב-`w:t` וב-`w:footnoteReference`, ואינו מטפל ב-`w:drawing`/`w:pict`/relationships/media; זו יכולת חסרה ונפרדת, שדורשת fixture ואזהרה.
